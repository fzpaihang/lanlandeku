## 0. 三十秒速查

**改前端（`*.html` / `assets/*.js` / `assets/style.css`）**

```bash
cd /e/workbuddy2/fzjh-rank
node --check assets/app.js                    # 1 语法（改哪个查哪个；环境见 §1.4）
python scripts/stamp_assets.py                # 2 【必做】刷 ?v= 缓存戳
# 3 推改动的 html/js/css（§4.5），等 Pages 30–90 秒
# 4 curl 确认 + 浏览器硬刷 + App 内 WebView 各看一眼
```

漏掉第 2 步是本项目最常见的事故：**代码上线了，但 App 内 WebView 还在跑缓存里的旧脚本，页面毫无变化**。

**改数据**（`data/**`）→ 一般由定时任务自动提交；要立即生效就手动触发 workflow（§5.2），或本地跑生成脚本再推（§5.4）。

**改后端 / API**（`api/`、`cloud/`、`worker/`）→ 重新生成部署包并部署（§6），静态站本身不受影响。

> 动手前先扫一眼 **§14 已知隐患清单**：`assets/lookup.js` 是死代码、两份 `names.json` 没有同步机制、5 转普查表没有自动上游——这些都不会报错，但改错地方会白忙一场。

## 4. 通道 A：前端代码改动

### 4.1 改代码

- 新筛选 / 排序 / 展示逻辑改 `assets/app.js` 或 `exp.js`；DOM 容器加在对应 HTML；样式加在 `style.css`。
- 只用现有 CSS 变量（§7.2），别写死颜色。
- 新增交互控件时同时考虑桌面表头与窄屏 `.sortbar`（§7.1）。

### 4.2 语法检查

```bash
node --check assets/app.js
node --check assets/exp.js
# assets/lookup.js 是死代码，不用检查（§14.2）
python -m py_compile scripts/*.py          # 若同时改了脚本
```

`node` 不在 PATH 时见 §1.4；这一步只做语法解析，不执行代码。

### 4.3 【必做】刷缓存戳

```bash
python scripts/stamp_assets.py
```

脚本扫 `index.html` / `exp.html` / `lookup.html` 里 `./assets/xxx.(css|js)?v=` 引用，把 `?v=` 换成文件内容的 md5 前 8 位；内容没变则不改文件，可重复执行。

**`lookup.html` 只引用 `style.css`、不加载任何 JS**：只改 JS 时它通常显示「无需改动」，但**改 `style.css` 时它也会被更新**（三个页面的 CSS 戳是同一个哈希）。输出示例（改了 CSS 的情况）：

```
index.html   更新  style.css=34089802 servers.js=160621b8 app.js=d7802752
exp.html     更新  style.css=34089802 exp.js=4186931e
lookup.html  更新  style.css=34089802
完成：3 个页面被更新
```

- **改了 JS/CSS 就必须跑**，并把改过的 HTML 一起推（戳写在 HTML 里）。
- **不要手改 `?v=`**，也不要用递增数字；哈希由脚本算。
- 只改 HTML 结构、没动 assets 时不用跑，但 Pages 本身仍有 30–90 秒缓存。

> 历史事故：给高手榜加「转数筛选」和「移动端排序」时，`app.js` 推上线了但没刷 `?v=`，App 内 WebView 继续跑缓存里的旧脚本，页面上完全看不到新功能；桌面浏览器硬刷能看到，两者不一致，排查了很久才定位。

### 4.4 本地预览

```bash
python scripts/serve.py 8791               # 默认 8791，静态站
# 浏览器打开 http://127.0.0.1:8791/index.html?s=taptap_4
```

`serve.py` 修了 Windows 上 `http.server` 调 `socket.getfqdn()` 遇到非 UTF-8 主机名会崩的问题，别直接用 `python -m http.server`。

行为细节（读源码确认）：

- **不打开浏览器**（全文无 `webbrowser`），只 print 一行 `serving ... at http://127.0.0.1:8791/`，要自己开浏览器；
- `serve_forever()` **阻塞**，Ctrl+C 才退出；
- 绑定 `127.0.0.1`，不对外网开放；端口取 `sys.argv[1]`，默认 `8791`；
- 设了 `allow_reuse_address = True`（缓解 TIME_WAIT），但**重复跑先停掉旧进程**，或换端口 `python scripts/serve.py 8792`；
- 静态根目录是项目根，所以 `http://127.0.0.1:8791/data/servers/taptap_4/gaoshoubang.json` 能直接读到线上同源数据。

带实时查询接口的联调见 §6.5。

### 4.5 发布

**常用：GitHub API 建 commit**（本地 git 与远端常分叉，API 方式不碰工作区）。模板与《APK 修改操作手册》§9.1 完全一致，只把 `files` 换成网页文件，例如：

```python
files = ['index.html', 'exp.html', 'lookup.html',
         'assets/app.js', 'assets/exp.js', 'assets/style.css']   # 按实际改动
```

顺序：`git/blobs` → `git/trees`（带 `base_tree`）→ `git/commits` → `PATCH /git/refs/heads/main`。
用 `base_tree` 很重要：CI 会往 `data/` 提交数据，全量 tree 会把它覆盖掉。

**备选：本地 git 直推**（仅当本地与远端一致）

```bash

git commit -m "网页：xxx"
env -u http_proxy -u https_proxy -u HTTP_PROXY -u HTTPS_PROXY -u ALL_PROXY -u all_proxy \
  timeout 90 git -c http.proxy= -c http.sslBackend=openssl push origin HEAD:main
```

## 5. 通道 B：数据改动

### 5.1 定时任务表（`.github/workflows/refresh.yml`）

cron 是 **UTC**，注释里写的是北京时间：

| cron (UTC) | 北京时间 | 分区 |
|---|---|---|
| `0 22 * * *` | 次日 06:00 | `taptap` 苍松迎客 |
| `55 15 * * *` | 当日 23:55 | `taptap_2` 白鹤亮翅 + `taptap_3` 丹凤朝阳 |
| `0 4 * * *` | 当日 12:00 | `taptap_4` 墨羽惊鸿 |
| `0 10 * * *` | 当日 18:00 | `4399` |

- 单区全量 5–8 分钟，五区一次 29 分钟，`timeout-minutes: 45`
- `concurrency: group: fzjh-data, cancel-in-progress: false` —— 串行，不取消进行中的任务
- 定时任务没有 inputs，靠 `github.event.schedule` 反查该抓哪个区；**手动触发时 `MODE` 非空，直接取 `PICK`，不走 `case`**
- **cron 字符串会先归一化**（`refresh.yml:78-80`）：`SCHED_N` 用 `tr -s` 压掉多余空格、`sed` 去首尾空格，再拿去 `case`。原因是 `github.event.schedule` 原样返回 cron，历史上出现过**双空格**，不归一化就会落到兜底分支误跑五区全量
- `case` 兜底确实是 `*) t='all' ;;`：任何没匹配上的 cron 都会五区全跑。**改 cron 必须同步改 `case` 分支**，两处一起改
- 想加新分区/新时段时，下面那段 `label` 映射也要一起补，否则摘要里显示「全部」
- 步骤顺序：连通性探测 → 抓榜单 → 抓档案 → 合并经验 → 重建昵称索引 → 提交 `data/`
- 提交前 `git fetch origin main && git rebase FETCH_HEAD`，最多重试 3 次，避免 non-fast-forward 丢整批数据

### 5.2 手动触发

```bash
# GitHub 网页：Actions → 刷新高手榜 → Run workflow
#   mode:   probe（只探连通性，不写文件） / board（只抓榜单） / full（榜单+档案）
#   server: all / taptap / taptap_2 / taptap_3 / taptap_4 / 4399
gh workflow run refresh.yml --repo fzpaihang/lanlandeku -f mode=full -f server=taptap_4
gh run list --repo fzpaihang/lanlandeku --limit 3
```

`merge-exp.yml` 是**只做合并、不请求接口**的手动流程：把已有 `profiles/` 的经验写回榜单并重写当天快照，适合两次抓取之间修正展示，或切换口径后修历史。

**它的两个副作用（改数据前必须知道）：**

1. **会提交 `data/`**。步骤里有 `git add -A data` → commit → `git fetch origin main` + `git rebase FETCH_HEAD` → `git push`（最多重试 3 次）。不是「只算不写」。
2. **和 `refresh.yml` 抢同一个并发组**。两者都是 `concurrency: group: fzjh-data, cancel-in-progress: false`，所以**串行排队、不会并行覆盖文件**；但手动跑 merge-exp 时若正好有定时任务在跑，要等它结束（最长 45 分钟）。`cancel-in-progress: false` 保证不会取消进行中的任务。

差异：两者 rebase 冲突都会整批放弃提交，但 `refresh.yml` 提交失败时会把 `data/` 留成 artifact 供补救，**`merge-exp.yml` 没有 artifact 兜底**——手动合并失败时数据只在 runner 里，runner 销毁就没了。`query.yml` 用的是另一个组 `fzjh-query`，不受影响。

### 5.4 经验快照口径（最容易出错的一块）

**背景**：`get_board`（排行榜）对不活跃玩家长期返回旧值，`get_user_info`（档案）更新更勤。`merge_exp.py` 把榜单 `exp` 改成档案整数值、原值存 `expBoard`，**名次 `rank` 保留游戏原始值，不按经验重排**。

**历史坑（v39）**：11-11 那批快照的 `exp` 是直接从排行榜取的浮点值，之后是档案整数值。两套口径相减 → 出现「+21.7 万 / −3.2 万」这类一眼假的增长。

**当前规则（改这块前必须遵守）**：

1. `exp-history.json` 里只保留 `src == "profile"` 的快照；11-11 那批已清掉。
2. `assets/exp.js` 的**当前值和基准都取快照**（`latest.exp[uid]` / `baseSnap.exp[uid]`），快照里没有才退回榜单行 —— 不能一边取榜单、一边取快照。
3. **基准选取（`assets/exp.js:268-278`，别记反）**：`latest` = 按 `ts` 排序后的最后一条；`cutoff = latest.ts - WINDOW_DAYS * 86400`（`WINDOW_DAYS = 3`）；然后**从最新往回**遍历，取第一条 `ts <= cutoff` 的快照，也就是「**3 天前或更早里最近的一条**」。只有一条都不满足（历史不足 3 天）时，才退回 `snaps[0]`（全历史最早那条）。
   - 保护：`if (baseSnap.ts === latest.ts) baseSnap = null`，基准撞上最新就不做对比。
   - `days = (latest.ts - baseSnap.ts) / 86400`；`days < 3` 时出「累计不足 3 天，日均暂不显示」横幅，`perDay = null`；`days >= 3` 才用 `grow / WINDOW_DAYS` 算日均。
   - 所以快照攒多之后，比的是**约 3 天前那条**，不是全历史最早那条。`merge_exp.py` 最多保留 60 条快照。
4. `merge_exp.py` 同一天重跑会**覆盖当天最后一条快照**（同 `ts` 差 ≤ `SNAP_GAP` 或同 `date`），所以一天只会有一条，不会人为造出第二条。
5. **不要**用 `profiles/` 目录重写基准：那批档案实测是 11-11 21:44 的，比榜单（11-13）还旧，拿它当基准等于倒着比。曾写过 `reset_exp_baseline.py`，已删除，别再恢复。

### 6.3 Issue 驱动的查询（`.github/workflows/query.yml`）

网页把 UID 拼成 Issue 标题提交：

```
[QUERY] 7257325
[QUERY] 7257325 @taptap
```

CI `issues.opened` 触发 → `scripts/query_issue.py` 调游戏接口 → 回帖 → 关闭 Issue → 成功时把 uid→昵称归档进 `data/extra-names.json`。

**归档不是「写文件再 commit」**，而是走 **GitHub Contents API**：`query_issue.py` 调 `cloud/archive_name.py::archive(prof)`，`GET data/extra-names.json?ref=main` 取当前内容与 `sha` → 本地合并/去重 → `PUT`（带上 `sha`）。

- 和 APK 端 `apk/archive_local.py::sync_async` **是同一套 GET→合并→PUT 写法**，两边都处理 `409` 冲突重试一次（0.6s / 0.8s）：后写的那次会因 `sha` 过期拿到 409，重读再写就能把并发修改合并回来，**不会静默互相覆盖**。
- **仍有残留风险**：若重试也撞车，Issue 端只返回 `conflict` / `http409`，**没有本地重试队列**，这条昵称就丢了；APK 端有 `pending_names.jsonl`，PUT 失败不清空、下次会补，更稳。
- **一共有三份归档实现**：`cloud/archive_name.py`（Issue）、`apk/archive_local.py`（APK）、`api/query.py::_archive`（Vercel 函数内联版，该文件 docstring 标注「当前暂不可达，保留」）。改归档字段或规则要三处对齐。
- `query.yml` 注入 `GH_TOKEN: ${{ github.token }}` + `GH_REPO`，`permissions: contents: write`；APK 端用的是 `gh.json` 里的 token。

⚠️ 一个 uuid 只保留一个有效会话密钥，**两个查询并发会互相作废旧密钥**，表现为 `errcode 20616`。所以 `concurrency: group: fzjh-query, cancel-in-progress: false` 是全局串行，不能按 Issue 号分组。

### 6.4 Worker 脚本

`worker/build-data.mjs`、`worker/make-dev-vars.mjs` 是 Node 侧的数据/开发变量构建脚本；`worker/src/` 下还有 `index.js` / `lookup.js` / `boards.js` / `names.js` / `profile.js` / `proto.js` 一套 Worker 模块（`index.js` 会 `import { lookup, rateOk } from "./lookup.js"`）。本次会话未改动它们，改之前先看脚本头部说明。

⚠️ **`worker/src/lookup.js` 与 `assets/lookup.js` 同名但毫不相干**：前者是活代码，后者是死代码（§14.2）。全局 grep `lookup.js` 时会同时命中三处（含 `worker/.wrangler/tmp/` 构建产物），别看错。

## 9. 硬规则与踩过的坑

| 坑 | 现象 | 正确做法 |
|---|---|---|
| **改了 JS/CSS 没跑 `stamp_assets.py`** | 代码上线但页面没变化（App 内尤甚），桌面硬刷却正常 | 每次改 assets 必跑，并把改过的 HTML 一起推 |
| 手改 `?v=` 或用递增数字 | 缓存不失效 | 用脚本算内容哈希 |
| **经验快照两套口径** | 「+21.7 万 / −3.2 万」假增长 | 只留 `src=profile` 的快照，前后端都取快照值 |
| 拿 `profiles/` 重置基准 | 档案比榜单旧，倒着比 | 已删除 `reset_exp_baseline.py`，别再恢复 |
| 同一天手动重跑 merge_exp 想造第二条快照 | 会被覆盖，一天只有一条 | 等第二天定时任务 |
| 当前值取榜单、基准取快照 | 又一次口径差 | `exp.js` 两边都取 `latest.exp` / `baseSnap.exp` |
| 转数筛选无条件显示 | 单档分区出现一排死按钮 | 去重后 `length<=1` 就 `hidden` |
| 排序入口只放在表头 | 手机端没有表头 → 无法排序 | 加 `.sortbar`，`@media (max-width:560px)` 才显示 |
| 移动端把「名次」换成「经验」 | 用户要的是默认名次 + 可手动切经验 | 默认 `rank/asc`，另给经验/等级按钮 |
| 分区列表加载失败静默回退 | 整页显示成别的区的数据 | 保留 `FZJH.listError` 横幅 |
| 写死颜色 / 混用两端配色 | 主题不一致 | 用 CSS 变量；注意网页 `--muted` ≠ APK `C_MUTED` |
| `git push --force` | 顶掉 Actions 提交的抓取数据 | 永远不要 |
| 全量 tree 覆盖式发布 | 把 CI 刚提交的 `data/` 覆盖掉 | GitHub API 用 `base_tree` 增量建 tree |
| 两个查询并发 | `errcode 20616` 互踢 | `concurrency` 全局串行 |
| 改 cron 忘了同步 `case` | 落到 `*) t='all'`，误跑五区全量 | 两处一起改 |
| 改 `hidden.json` 不重建索引 | 隐私名单不生效 | 重跑 `build_lookup_index.py` |
| 名次按经验重排 | 与游戏内榜单不一致 | `rank` 保留原始值 |
| **`assets/lookup.js` 是死代码** | 改了半天页面毫无变化 | 改 `index.html` / `exp.html` 对应的活脚本；`lookup.js` 勿动（§14.2） |
| **只改一份 `names.json`** | 两个生成脚本看到两套武学名，产物悄悄不一致 | 两份一起改并校验 md5（§10.5、§14.3） |
| **cron 字符串没归一化** | `github.event.schedule` 带双空格 → 落到 `*) t='all'` 误跑五区全量 | `refresh.yml:78-80` 的归一化别删；改 cron 同步改 `case` |
| **手动跑 merge-exp 以为不写数据** | 它也会 `git add -A data` 提交，还可能排在定时任务后面 | 看 §5.2，`concurrency: fzjh-data` 串行 |
| **归档三份实现不同步** | 改了 Issue 端字段，APK / Vercel 端还是旧结构 | 三处一起改（§6.3） |
| **5 转普查表当活数据** | 以为它会随抓取更新，其实是一次性快照 | 见 §14.5；删它会让 APK 字体缺字 |
| **Windows 下用 `split('/')` 取分区名** | 打印出来全是 `data` | 用 `os.path.basename(os.path.dirname(p))`（§1.4） |
| **`node` 不在普通终端 PATH** | 照抄 `node --check` 报「不是内部或外部命令」 | 用 §1.4 的绝对路径或跳过 |

## 10. 常用脚本模板

### 10.1 发布（GitHub API，通用）

```python
import base64, io, json, urllib.request
TOK = io.open('E:/workbuddy2/_agent_tmp/gh_token.txt', encoding='utf-8').read().strip()
REPO, API = 'fzpaihang/lanlandeku', 'https://api.github.com'
def call(m, p, pl=None):
    d = json.dumps(pl).encode() if pl is not None else None
    r = urllib.request.Request(API + p, data=d, method=m)
    r.add_header('Authorization', 'token ' + TOK)
    r.add_header('Accept', 'application/vnd.github+json')
    r.add_header('Content-Type', 'application/json')
    op = urllib.request.build_opener(urllib.request.ProxyHandler({}))
    with op.open(r, timeout=60) as x:
        return json.loads(x.read().decode())

base = call('GET', '/repos/%s/git/ref/heads/main' % REPO)['object']['sha']
ts = call('GET', '/repos/%s/git/commits/%s' % (REPO, base))['tree']['sha']
files = ['index.html', 'exp.html', 'lookup.html', 'assets/app.js', 'assets/style.css']
entries = []
for f in files:
    sha = call('POST', '/repos/%s/git/blobs' % REPO,
               {'content': base64.b64encode(open(f, 'rb').read()).decode(),
                'encoding': 'base64'})['sha']
    entries.append({'path': f, 'mode': '100644', 'type': 'blob', 'sha': sha})
tree = call('POST', '/repos/%s/git/trees' % REPO, {'base_tree': ts, 'tree': entries})
new = call('POST', '/repos/%s/git/commits' % REPO,
```

### 14.2 隐患 A：`assets/lookup.js` 是死代码（A2）

**事实（实测）**

- `grep -rn "assets/lookup.js" --include=*.html .` → **零匹配**。三个 HTML 里没有任何一处引用它。
- `lookup.html:17` 只引用 `./assets/style.css?v=...`，**不加载任何 JS**。
- `scripts/stamp_assets.py` 只扫 HTML 里的 assets 引用，所以它**也不会**为 `lookup.js` 刷戳。
- 结论：改 `assets/lookup.js` **完全不会生效**，既不报错也不降级提示。

**最容易踩的混淆**

| 文件 | 状态 | 谁在用 |
|---|---|---|
| `assets/lookup.js` | **死代码** | 无人引用 |
| `worker/src/lookup.js` | 活代码 | 被 `worker/src/index.js` 的 `import { lookup, rateOk } from './lookup.js'` 使用 |
| `worker/.wrangler/tmp/dev-*/index.js` | 构建产物 | 只是打包后的副本，里面的 `// src/lookup.js` 是注释 |

全仓 grep `lookup.js` 会同时命中这三处，**别把 Worker 侧的命中当成 `assets/lookup.js` 还活着**。

**当前决定：保留文件、标注废弃、不删。**

删除前必须确认：`build_font_subset.py` 等脚本没有拿它扫字符集、`serve_api.py` 没有间接引用、Worker 构建没有依赖它。
若将来要删：全仓 grep 确认零引用 → 删除 → 跑一次 `stamp_assets.py` 与 `node --check` 确认无副作用。

### 14.3 隐患 B：两份 `names.json` 没有同步机制（B3）

**事实（实测）**

| 文件 | 大小 | md5 前 12 位 |
|---|---|---|
| `data/names.json` | 64,314 B | `8325e44d8a1a` |
| `apk/names.json` | 64,314 B | `8325e44d8a1a` |

内容**完全相同**，但**是两个独立文件，仓库里没有任何脚本负责同步它们**。

**各自的读者与生效范围不同**

| 文件 | 谁读 | 改动后怎么生效 |
|---|---|---|
| `data/names.json` | `scripts/build_names.py`（产物）、`scripts/fetch_profiles.py` | 只被本地脚本读，**推仓库即可**；网页运行时不读它 |
| `apk/names.json` | `scripts/build_skill_class.py`（774 个武学 id）、`scripts/build_api_zip.py`（复制进云函数包）、APK 内置 | **不在热更包的 `FILES` / `EXTRA` 里** → 改它**必须重打 APK + 重装** |

**风险**：改武学/装备名时只改一份，两个生成脚本就会看到两套名字 —— 榜单详情、武学分类、云函数返回悄悄不一致，而且**没有任何报错**。

**当前决定：不加同步脚本、不改代码**，改用流程约束：

1. 改名字时 `data/names.json` 与 `apk/names.json` **一起改**（或重跑 `build_names.py` 后手动复制）；
2. 改完跑 §10.5 的 md5 校验；
3. 若涉及 `apk/names.json`，记得这属于必须重打 APK 的改动，不能只发热更。

**将来要根治**（需单独确认方案）：让 `build_names.py` 一次写两份，或改为构建期从 `data/names.json` 复制到 `apk/`；后者仍要重打 APK，但能消除手工同步。

### 14.4 隐患 C：CI 并发与归档竞态（B1 / B2）

- `refresh.yml` 与 `merge-exp.yml` 共用 `concurrency: group: fzjh-data, cancel-in-progress: false` → 串行排队，**不会并行覆盖 `data/`**；但手动 merge 可能等 45 分钟，且 `merge-exp.yml` **没有 artifact 兜底**（refresh 有），提交失败数据只留在 runner 里。
- 三份归档实现（`cloud/archive_name.py` / `apk/archive_local.py` / `api/query.py::_archive`）都是 `GET → 合并 → PUT(sha)`，各自处理一次 409 重试。**Issue 端没有本地重试队列**：极端并发下重试也撞车，该条昵称会静默丢失；APK 端有 `pending_names.jsonl` 兜底，更稳。
- 改归档字段（例如加 `a` 别名、`sn` 分区名）或改 `GH_MAX_ITEMS` 上限时，**三处 + `build_lookup_index.py::load_extra_names()` 要一起看**，否则索引与仓库里的结构会对不上。
- 当前决定：不动代码，只在 §6.3 写清链路与风险。

### 14.5 隐患 D：5 转普查表没有自动上游（B5）

**事实**

- `export_5zhuan` **只出现在 `build_lookup_index.py` 的 docstring 注释里**，仓库和 CI 里都没有这个脚本。
- git 历史只有两条：`e1f1d8a 新增：苍松 5 转玩家（7787 人，8 万普查导出）`、`2395fd2 5 转名单：移除 2 名隐藏玩家 [skip ci]`；当前 `players` 7785 人，顶层键 `src` / `filter` / `count` / `players`。
- 定时任务、抓取脚本、索引重建都**不会更新它**；重建索引只是「读它」。

**影响**

- 不会「哪天突然断供」（本来就没有自动供应），但它是**一次性静态快照，不会随游戏更新**。要刷新必须重做那次普查导出，而导出脚本不在仓库里，等于要重写。
- `build_lookup_index.py::load_zhuan5()` 读不到文件时 `return []`，**静默降级** —— 索引少 7785 个老玩家昵称，不报错、不告警。排查时看 §10.6。
- **额外关联**：`scripts/build_font_subset.py` 也读它，把昵称里的汉字收进 APK 字体子集。**删了这个文件，APK 字体缺字会出豆腐块**（Kivy 不做字体回退）。

**当前决定：保留文件、标注来源、不改代码。**

### 14.6 隐患 E：命令环境差异（C1 / C2 / C3）
