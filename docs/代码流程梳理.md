## 6. 流程痛点与本次工具化

### 6.1 痛点

| 痛点 | 以前怎么做 | 后果 |
|---|---|---|
| 发布要手写脚本 | 每次在 `_agent_tmp` 新建 `publish_vXX.py`、`cleanup_*.py` | 容易漏 `base_tree`、漏文件、把 `code.zip` 单独推 |
| 发布前检查靠记忆 | 翻手册逐条对 | 忘跑 `stamp_assets.py`、忘重打包、忘了 `names.json` |
| `git status` 不可信 | 本地 git 落后线上约 27 个版本 | 误判「哪些文件要发」 |
| API 发布绕过 `.gitattributes` | 直接传原始字节 | CRLF 文件在 GitHub 上显示「整篇 1277 行都改了」 |

### 6.2 新增的三个脚本（本次）

| 脚本 | 作用 | 是否影响运行 |
|---|---|---|
| `scripts/preflight.py` | 发布前 10 项自检：Python/JS 语法、缓存戳、热更包 md5+验签+清单、等级口径、两份 names、隐私名单（含三份副本一致性）、字段级隐藏、经验快照窗口 | 否，只读 |
| `scripts/publish.py` | 统一发布：`blob→tree(base_tree)→commit→PATCH`，自动跳过无变化文件、强制 `code.zip`+`version.json` 成对、拒绝敏感文件、按 `.gitattributes` 归一化换行 | 否，只写远端 |
| `scripts/check_drift.py` | 本地 vs 远端 main 的真实差异（按 git blob sha 比对，区分「仅换行差异」） | 否，只读 |

用法：

```bash
python scripts/preflight.py --fix                 # 自检 + 自动刷缓存戳
python scripts/publish.py --check "说明" 文件...   # 预览将要发生的改动
python scripts/publish.py "说明" 文件...           # 正式发布
python scripts/check_drift.py --all               # 本地与线上差在哪
```

### 6.3 现在的标准发布流程

```bash
# 1. 自检（会顺便告诉你要不要重新打包热更）
python scripts/preflight.py

# 2. 需要时：打包热更（自动 +1 版本、签名）
python scripts/pack_update.py "这次改了什么"

# 3. 预览改动，确认没有多余文件
python scripts/publish.py --check "热更 vNN：xxx" apk/*.py apk/update/code.zip apk/update/version.json

# 4. 发布
python scripts/publish.py "热更 vNN：xxx" apk/*.py apk/update/code.zip apk/update/version.json
```

## 10. 第二批改动（E / F / H + 本地 git）

### 10.1 E：cron 映射抽成脚本

`refresh.yml` 原来在一个 `run:` 里用两段 shell `case` 做「cron→分区」和「分区→中文名」，
改 cron 要同时改三处（`on.schedule` 列表、第一个 `case`、第二个 `case`），漏一处就静默跑错区。
现在：

- 映射表在 `scripts/plan_refresh.py` 的 `SCHEDULE_MAP` 与 `LABELS`；
- 工作流只做 `python scripts/plan_refresh.py ... >> "$GITHUB_OUTPUT"`；
- 任务摘要拆成独立一步，用 `steps.t.outputs`，内容与以前一致。

本地验证（已逐条跑过）：5 条 cron、双空格、首尾空格、未知 cron（→`all`）、
手动 `mode` + 6 个分区、`all`，输出与旧 shell 完全一致。

### 10.2 F：merge-exp 失败兜底

`merge-exp.yml` 原来在 rebase 冲突 / 连续 push 失败时直接 `exit 1`，数据只留在 runner 里。
现在补了 `actions/upload-artifact@v4`（`if: failure()`，保留 7 天），与 `refresh.yml` 一致。
同时把漏掉的 `yyh` 加进手动选项——以前应用汇没法单独合并经验。

### 10.3 H：删除重复入口

`api/index.py` 与 `cloud/fc_index.py` 内容完全相同（18,790 B），前者是早期 Vercel 入口，
`vercel.json` 只登记了 `api/query.py`，且 Vercel 已停用。删除远端这一份，本地同步删除。
`scripts/serve_api.py` 的 docstring 一并纠正（它加载的是由 `cloud/fc_index.py` 生成的 staging 副本）。

### 10.4 G：本地 git 对齐

本地 HEAD 停在 v29（`5344e87`），落后远端 27 个版本；`git status` 显示的 20 多个「修改」

### 10.5 为什么 A / B 没做

- **A（合并两份 `fetch.py`）**：协议层是 App 查询与每日数据抓取的共同命门。合并要么让
  `scripts/` 依赖 `apk/` 的模块（CI 引入 Android 侧代码路径），要么抽新模块进热更包
  （`FILES` 变更 + 重新打包 + 真机验证）。两者都无法做到「改完立刻可证明零影响」，
  不符合「不影响现有功能才做」的前提。
- **B（抽公共等级模块）**：同样要在热更包里新增一个模块，一旦漏打包，
  `import` 失败会直接让 App 打不开查询页；收益只是去掉十几行重复。
  当前用 `preflight.py` 的数值比对 + staging 告警来防漂移，成本更低。

**结论**：等游戏协议下次真的要改时，把 A + B 一起做（那时本来就要回归测试），
比为整洁单独动一次更划算。
